# AGENTS.md

## NEVER LOSE DATA (the most important rule — applies to every change and every deploy)

Production data (members, cards, orders, payments, products, facilities, visitors, logs…) must survive every update we upload. Before a change ships, check it for loss — and say so in the hand-off.

- **Migrations only ADD.** New tables, new nullable/defaulted columns, widened enums. Never `dropColumn`/`dropIfExists`/`truncate`/narrow a column or enum in `up()` on a table that holds data. A reshape is copy → verify → drop in a LATER release, and the copy must be in the same migration that creates the target.
- **Deploy with `php artisan migrate --force` only.** Never `migrate:fresh`, `migrate:refresh`, `migrate:reset`, `db:wipe`, or `db:seed` (the full seeder) on a server. `PermissionSeeder` re-syncs the `admin`/`editor`/`viewer` roles and DROPS any permission an admin gave them by hand — a new permission is added by a migration (see `2026_10_23_120000_add_view_visitors_permission.php`), not by re-running it. `AreaSeeder::run()` overwrites edited names/borders.
- **Back up first.** `mysqldump` the database before `migrate` on every deploy, and keep it until the release is confirmed.
- **Tests never touch a real database.** `php artisan test` here defaults to the LIVE database (cached config) and `RefreshDatabase` runs `migrate:fresh`, which DROPS EVERY TABLE. On 2026-10-22 a test run wiped the whole local `ibusiness_medical` this way. Before running any test: confirm the target with `php artisan tinker --execute='echo DB::connection()->getDatabaseName();'` under the SAME env, and use a database whose name ends in `_test`. If you cannot prove which database a run will hit, do not run it.
- **Writes must be re-runnable and non-destructive**: importers key on a unique legacy id and skip what exists; commands have `--dry`; nothing deletes or overwrites a row it did not create.

## Error Logging (required for all new features)

Every new feature must log errors on both sides to make debugging possible:

### Backend
- Wrap risky operations (payments, callbacks, DB writes) in try/catch.
- Use `Log::error()` / `Log::warning()` with context (route, payload summary, exception message + stack).
- Never swallow exceptions silently.

### Where failures go (do not undo)
- `storage/logs/laravel-YYYY-MM-DD.log` keeps **today only** (`LOG_DAILY_DAYS=1`).
- `storage/logs/failures.log` is PERMANENT (never rotated or pruned; one JSON object per line). It gets every API answer ≥ 400 (`App\Http\Middleware\LogApiFailures`, a GLOBAL middleware limited to `api/*` so it also sees auth 401s, throttle 429s and unknown-URL 404s), every client crash report (`ClientErrorController`) and every `error`-level log from anywhere (`failures_errors` in `LOG_STACK`). Only field NAMES are logged, never values.
- Read it with `php artisan logs:failures` (grouped; `--days=N`, `--all`, `--status=500`, `--examples`); after fixing, `--mark-reviewed` so the next run shows only new ones. A SessionStart hook prints the summary whenever Claude opens this project — when it shows failures, offer to fix them.

### Frontend (JS/Blade)
- Catch errors and report them via the existing endpoint: `POST /api/v1/client-errors`
  (`App\Http\Controllers\Api\V1\Guest\ClientErrorController` → `client_error_logs` table, viewable at `/admin/client-error-logs`).
- Payload: `message` (required), `stack`, `fatal`, `route`, `extra` (e.g. order_code, step).

## Dashboard UI (required)
- Every new admin entity MUST get a sidebar entry in `resources/js/Layouts/AppLayout.vue`
  using `SidebarLink`/`SidebarDropdown` with a related inline-SVG icon in the `#icon` slot.

## Conventions
- Laravel 12. Migrations: anonymous classes in `database/migrations`.
- Enums: string-backed, per-domain folder under `app/Enums/<Domain>/` with `values()`, `getOptions()`, `getLabel()`, `label()`.
- Models: `$fillable` + `casts()` method, relations as methods.
- Rate limits ALWAYS name their counter: `throttle:10,1,api.partner.orders.store`, never bare `throttle:10,1`. A bare one is keyed by IP alone, so every throttled route shares one counter — and every storefront call comes from the storefront's ONE server IP, so its card lookups used up the order limit. Same rule on the website (`../deilar`, where it gave buyers a 429 at checkout).
- **Same-named enums / classes: check the `use` line before calling a method.** `PaymentTypeEnum` exists in both `App\Enums\Order` and `App\Enums\Membership` with different cases and different methods. Before calling any static method on an enum (or any class whose short name exists in more than one namespace), read the file's `use` import, open the class it resolves to, and confirm the method is defined THERE — never assume it from a similarly named class elsewhere. After adding or renaming an enum method, `grep -rn "::method(" app` and check every caller's import. Verify with `php -l` AND by actually exercising the route/request (or a test) — a missing static method is a runtime 500, not a syntax error.
- **Nothing may overflow its frame (filters, toolbars, button rows).** A row of buttons or inputs inside a grid cell must fit the cell at every width: give the row `flex-wrap` and each button a `min-w-*` (never `whitespace-nowrap` + `flex-1` on 3+ siblings in a narrow cell), and when a group needs more room than one grid column gives it, make it `col-span-full` instead of squeezing it. If a filter grows, reorder the blocks so wide groups sit on their own row. Before finishing any UI change that adds or widens a control, check it at mobile, tablet and desktop widths (and RTL) — if the content can overflow the frame, it is a bug, not a styling nit.
- **Phone and National ID are unique, from EVERY write path.** `users.phone` and `memberships.national_id` belong to one live (non-soft-deleted) record. The models enforce it (`GuardsUniqueIdentity` in `User::booted` / `Membership::boot`: a `ValidationException` on any save that sets or changes the value), so imports, jobs, console commands, the app and the website are covered, not just the admin forms. Form requests keep their own `unique` rules for friendly messages, and the admin form checks live via `GET /api/member-field/check`. Never bypass it: no `DB::table(...)->insert/update`, `saveQuietly`, `Model::withoutEvents` or raw SQL on these two columns. An untouched legacy duplicate stays editable (only a changed value is checked) so admins can clean them up; the list's "Duplicate phone / National ID" filters find them. A new write path (new endpoint, importer, command) must go through Eloquent `save()` and be covered by a test. Relatives (`family_members`) are not covered by this rule.

## Orders Feature Notes
- `orders` table: statuses are DB enum columns backed by `App\Enums\Order\{PaymentStatusEnum,DeliveryStatusEnum}`; payment type by `PaymentTypeEnum` (`cod`, `transfer-wallet`).
- Delivery status updates come from an external delivery callback — must be logged on failure/success.
- Set `payment_status` AND `delivery_status` explicitly when creating an order. They have DB defaults, so the model returned by `create()` carries null and any resource reading `->status->value` blows up.
- `order_products` is an ARCHIVE, not a join table. Every line copies `name` (the whole translation map), `slug`, `image`, `quantity`, `old_price`, `new_price`, `line_total`, `cost_price` and `profit_price` at the moment of sale. Build lines with `OrderProduct::fromProduct()` — never read a placed order's prices back through `product_id` (which is nullable precisely so a deleted product does not take the order's history with it).
- `orders.delivery_cost` / `delivery_price` / `delivery_profit` archive the delivery arrangement an order was placed under, the way `order_products` archives `cost_price`/`profit_price` per line. `delivery_price` is added to BOTH `total_amount` and `total_amount_before_discount`, so the gap between them stays exactly the membership discount. The profit is ALWAYS recomputed as `price - cost` — by `StoreOrderRequest::delivery()` on the API and by `UpdateOrderAction` in the admin — never taken from whatever a caller or a form posted. The partner resource shows the buyer `delivery_price` only; cost and profit are ours.
- Storefront orders arrive at the key-gated `/api/v1/partner/orders`. `$request->ip()` there is the storefront's SERVER — the buyer's own IP and user agent come in the request body, which is why the endpoint needs the partner key.
- The order code is the buyer's only credential: random, 8 characters, ambiguous letters excluded (`Order::generateCode()`). Never make it sequential.
- Wallet receipts are a `receipt` media collection on `Order`: uncapped and APPEND-ONLY. Any number of files, added at any time, from the buyer's order page or the admin edit form — nothing in the app deletes or replaces one. An admin who does not believe a receipt moves `payment_status` (attributed and dated in `order_logs`); deleting the evidence records nothing. `Order::awaitingReceipt()` is "none yet" (the chase-the-buyer badge); `Order::acceptsReceipts()` is "more may be sent" (true for the life of a transfer order) — do not collapse them. A receipt is a CLAIM — it never moves `payment_status`; an admin confirms it against the wallet.

## Permissions & the super admin

- **`super_admin` passes every permission check, always** — via `Gate::before` in `AppServiceProvider`, on the strength of the ROLE, not on what happens to sit in `role_has_permissions`. Before that it only held whatever `PermissionSeeder` last synced, so adding a permission to `UserPermissionEnum` and shipping the feature that used it locked the super admin out until somebody re-ran the seeder. That is exactly how `manage settings` came to 403 the one account meant to reach everything. Adding a new permission to the enum now needs no seeder run for the super admin to have it.
- The callback returns **null**, not false, for everyone else. False is a verdict and would end the check before the real permission lookup ran; null means "no opinion, carry on".
- **Ask the Gate, never the permission tables, when the answer must respect that.** `can()` / `canAny()` run the Gate; Spatie's `hasPermissionTo()` / `hasAnyPermission()` read `role_has_permissions` directly and cannot see the super-admin grant. `EnsureAdminAreaAccess` used `hasAnyPermission` and so turned a super admin away at the door of the admin area even though every route inside would have let them in — it uses `canAny` now. Spatie's own `permission:` route middleware already uses `canAny`, which is why routes worked and the area gate did not.
- `User::effectivePermissionNames()` is what the front end gets (`authUserPermissions` in `HandleInertiaRequests`, `auth.user.permissions` in `ShareUserPermissions`) — the full enum for a super admin, the granted rows for everyone else. Do not go back to `getAllPermissions()` in those two places: the admin UI hides its buttons on this list, so a list narrower than the Gate gives a super admin routes they can reach by typing the URL behind links the page will not draw.
- `permissions` rows still matter for every OTHER role, so a new permission must still be added to `UserPermissionEnum` and seeded (`php artisan db:seed --class=PermissionSeeder`) before a non-super role can be granted it. Run it after adding one.
- `manage own contact messages` exists as a row in `permissions` but is deliberately absent from `UserPermissionEnum::all()` — see the Contact Enquiries notes below. It is a leftover, not a gap; do not "fix" it by re-adding it to the enum.
- Regression cover: `tests/Feature/Admin/SuperAdminPermissionsTest.php`.

## Audit Logs (required)
- Every create/update/delete/status-change on orders and products MUST be recorded:
  - `OrderLog::record($orderId, $adminId, $action, $oldValues, $newValues, $request)` → `order_logs`
  - `ProductLog::record(...)` → `product_logs`
  (same pattern as `FacilityLog`: old/new values JSON + changed_fields + ip/user_agent).
- Reads count too: opening an order (`OrderLog::ACTION_VIEWED`) or its edit form
  (`ACTION_EDIT_VIEWED`) is filed by `OrderLog::recordVisit()`, which folds a repeat
  visit by the same admin inside `VISIT_THROTTLE_MINUTES` into the one already logged —
  otherwise a refreshed page buries every real change. A failed log must never cost the
  admin the page: warn and carry on.
- An order's `order_code`, `ip_address` and `user_agent` are never editable. The code is
  the buyer's only credential; the other two are the only record of where the order came
  from (the buyer's, forwarded by the storefront — not the caller's).

## Shipping with ABS Courier (order → courier)

- The button lives on the order SHOW page and calls `POST /api/v1/create-shipment`, **not** `create-pickup`. `create-pickup` takes AWBs that already exist and only schedules a collection — it cannot start a delivery. Passing `locationId` (from `ABS_LOCATION_ID`) on `create-shipment` books the pickup in the SAME call, so one request both ships the parcel and asks for it to be collected. Do not add a second `create-pickup` call.
- `orders.customer_governorate` / `customer_city` are free Arabic text the buyer typed; ABS routes on numeric `governorateId` / `cityId`. `AbsAddressMatcher` narrows the ABS dropdown to a best guess (alef/ta-marbuta/ya variants folded, the `ال` article ignored, Arabic-Indic digits normalised) and the admin confirms it in the dialog. It returns null on an AMBIGUOUS containment match rather than picking the first row — a wrong governorate sends a parcel to the wrong end of the country. `ShipOrderRequest` requires both ids and never reads them off the order: the confirmation IS the authorisation.
- `AbsShipmentPayload` is the ONE mapping from our columns to their fields. The preview and the submit both build through it, so what an admin approves on screen is what gets posted — a second mapping written "just for the preview" is a preview that can lie.
- `cash` (COD) is set outside the payload's `array_filter` on purpose: zero is a real instruction ("collect nothing, it is paid"), and filtering it out turns a prepaid order into one with no COD instruction at all. Only `PaymentTypeEnum::COD` collects anything; a wallet transfer sends `0`. The figure is `total_amount - total_paid`, floored at zero.
- Phones are normalised to E.164 (`01070274943` → `+201070274943`); a number already starting `+` is left alone so a foreign number is never rewritten into an Egyptian one.
- Never send `awb`, `businessLocationId` or any branch id — ABS derives all of them, and the spec says not to.
- `ShipOrderAction` calls ABS **outside** any transaction, then writes the order and its logs inside one. An HTTP call must not hold row locks, and a refusal must leave the order untouched. `abs_awb` is UNIQUE and is the guard against double-booking (two couriers, two delivery fees). The one unfixable case — ABS accepts and our write fails — is logged at error level with the AWB and surfaced to the admin as "do NOT ship it again", because it can only be reconciled by hand.
- A 2xx carrying no AWB is treated as a FAILURE. An order marked shipped with nothing to track is worse than one that visibly failed to ship.
- Shipping writes `OrderLog::ACTION_SHIPPED` (with the AWB and the ids actually booked, so a misdelivery can be traced to a bad match vs a bad address) plus the usual `delivery_status_changed`. Status goes to `processing`, never `on-delivery` — that is the courier's news to tell.
- Leaving `ABS_API_KEY` unset hides the button (`AbsClient::isConfigured()`, the `absConfigured` page prop), the same way a missing Gemini key hides the AI helpers. `ABS_BASE_URL` defaults to STAGING so a half-configured install cannot book a real courier.
- Tests: `tests/Feature/Admin/OrderShipTest.php`, entirely behind `Http::fake()`. Nothing in that file may ever reach the real API — a leak books an actual courier to a real customer's address.

## Online payment with Paymob, and the cash-on-delivery fee

- `payment_type` gained `paymob`; `payment_status` gained `refunded`. `Order\PaymentTypeEnum::offlineValues()` exists ONLY on the Order enum. The **membership** requests use a different enum, `App\Enums\Membership\PaymentTypeEnum` (`yearly`/`monthly`), and validate with its `values()` — see the same-named-enum rule under Conventions.
- **COD fee**: `shop_cod_fee` in `ShopDelivery` (edited at /admin/setting). Read server-side in `OrderController::store` and added to BOTH totals like delivery, archived in `orders.cod_fee`. Only a `cod` order carries it; a caller's `cod_fee` is never read. **0 = no fee, and every client draws nothing** (`/mobile/shop` → `cod_fee`, `/partner/shop-settings` → `codFee`).
- **Flow**: `store` writes the order (payment `pending`), then `StartPaymobPayment` calls Paymob's Intention API and the response carries `payment.checkout_url`. If the gateway is down the order still exists and `payment.checkout_url` is null; clients retry via `POST …/orders/{code}/pay` (mobile + partner). Each attempt uses a fresh `special_reference` (`CODE`, `CODE-2`…); `PaymobTransaction::orderCode()` strips the suffix. A membership retry reuses the open unpaid `SUB` payment, and `StartSubscription` re-prices it (amount + months) to today's settings first — it once charged a buyer 600 after the price had been set to 5.
- **"Pay online instead"**: a `cod` / `transfer-wallet` order switches to `paymob` only through `POST …/orders/{code}/pay` with `switch_to_online: true` (a plain "pay now" never changes the type). `Order::canSwitchToOnline()` decides — pending, nothing paid, NO receipt filed (a receipt claims a transfer already happened; paying on top is paying twice), not shipped, not failed — and clients get it as `can_switch_to_online`. `SwitchOrderToOnlinePayment` takes the COD fee off BOTH totals under a row lock and logs `payment_type_changed`. The website checkout opens on online payment whenever Paymob is configured.
- **One place decides what a result means**: `ApplyPaymobTransaction`, fed by the server callback (`POST /api/v1/paymob/callback`), the buyer's browser return (`GET /api/v1/paymob/return/{code}`) and the admin's "Check with Paymob" button. Idempotent; never un-pays a paid order; a paid amount ≠ `total_amount` is NOT accepted whatever the flag says. Callbacks are public — the HMAC (`PaymobHmac`) is the only credential, checked before anything touches an order.
- **Card form = Paymob Pixel, never our own inputs.** Clients get `payment.client_secret` + `payment.public_key` (orders, `/membership/subscribe`, `/card/{n}/subscribe`) and mount Paymob's hosted Pixel form (pinned `paymob-pixel@1.2.8`; `checkout_url` is the fallback). **Pixel draws cards, Apple Pay and Google Pay only — never a mobile wallet**: a wallet-only payment mounted in it is an empty form. So every payment answer carries `form`: `pixel` (mount Pixel) or `redirect` (open `checkout_url`, Paymob's hosted page, which takes wallets). `PaymobClient::formFor()` decides it — `redirect` when every integration offered is a wallet one. Clients follow `form`; they never decide it from the channel themselves. Card numbers must never pass through our code or servers (PCI-DSS); `afterPaymentComplete` in the browser proves nothing — the signed callback does, so clients re-read the order. Every intention also sends `extras` (`app`, `kind`, `env`, `host`, order code / card number, channel) so Paymob's dashboard shows where a payment came from; keep those free of names, phones and addresses. A buyer with no email is sent `noemail@deilar.com` (Paymob rejects a blank/`NA` one).
- **Logging**: every HTTP exchange is one `order_payment_logs` row written by `PaymobClient::exchange()` / `recordInbound()` — URL, headers, request body as sent, HTTP status, response body as received, gateway code (`txn_response_code`), start/finish/`duration_ms`. Shown in the order's **Payment** tab (with the gap since the previous exchange). Only credentials are masked (Authorization header, `api_key`, the auth `token`). Order-level actions also go to `order_logs` (`payment_initiated/callback/checked/accepted/rejected/refunded`, `refund_failed`, `receipt_emailed`). A log write failing never fails the payment.
- **Receipt**: `SendOrderReceipt` mails `OrderReceiptMail` to `customer_email`, else the member's own email; no address = nothing sent, no error. COD/transfer: at order placement; Paymob: when the payment is accepted. Once per order unless the admin uses "Email receipt".
- **Admin**: Payment tab buttons — Check with Paymob (needs `PAYMOB_API_KEY` for the inquiry token), Refund (full/partial, `RefundPaymobPayment`; the order only becomes `refunded` when Paymob confirms), Email receipt.
- **.env**: `PAYMOB_SECRET_KEY`, `PAYMOB_PUBLIC_KEY`, `PAYMOB_HMAC_SECRET`, `PAYMOB_INTEGRATION_IDS`, `PAYMOB_API_KEY`, `PAYMOB_RETURN_URL`, `PAYMOB_ALLOWED_RETURN_URLS` (return URLs a client may ask for — anything else is ignored, so the return redirect cannot be an open redirect). Blank secret key hides online payment everywhere. Set the integration's "Transaction processed callback" to `https://HOST/api/v1/paymob/callback`. Config is cached on this host: run `php artisan config:cache` after editing .env.
- Tests: `tests/Feature/PaymobPaymentTest.php`, entirely behind `Http::fake()`.

## Trial cards, subscriptions & relatives — THE CONTRACT (same text in all three projects)

> Deilar is three projects: `ibusiness_medical` (Laravel backend — owns every rule and every number), `deilar` (the website) and `deilar-mobile-new` (the app). The website and the app are CLIENTS: they relay what a member typed and DRAW what the backend answers. If you change a rule, change it in `ibusiness_medical` first and update this section in all three files in the same change.

1. **Free trial card.** A member makes one from the app or the website with ONLY: the phone they signed in with (proved by the SMS code), a **name** (no national ID). It works immediately, `plan = trial`, and expires after `membership_trial_months` (default **1 month**; admin setting). It holds the OWNER ONLY — never a relative.
2. **One trial per phone — while that card exists.** Enforced by the backend: `trial_claims` (DB unique index on `phone`; a claim whose card was deleted, soft or hard, is stale and is released by `StartTrialCard::releaseStaleClaims()` into the new card's `member_logs` as `released_trial_claims`, so a member whose card was deleted can start again) and any other account with the same phone that holds a card. The national ID is NOT asked for any more (it can be added later in the profile). A second device signs into the SAME account (login is by phone) so it just sees the same card; another account row with the same phone is refused (`reason`: `phone_taken`, `already_has_card`). Never weaken this, never add a client-side "retry with another phone".
3. **The backend decides what a card IS.** `Membership::state()` → `pending | trial | trial_expired | active | expired | inactive`; clients get it as `status` (`MembershipStatus::forCard` for anyone scanning, `forMember` for the signed-in owner). Clients NEVER compute expiry, price, "can add relatives" or the profile percentage themselves.
4. **Expired card = a big RED sign.** Whenever a card is scanned or opened (QR page, the website's `/membership/{number}`, the app's card screen) and `status.expired` is true (a trial that ended OR a paid card that lapsed) the page leads with a large red "CARD EXPIRED" sign and three options: **Subscribe now with Paymob** (only if `status.can_pay_online`; hidden when the price is 0 or Paymob is unset), **Call customer service** (`tel:` the phone), **Message customer service** (WhatsApp). Contacts come from `status.contact` (admin settings) — never hard-code a number. A running trial shows a small amber banner with the days left. An expired card earns NO member price (`Membership::isCurrent()`).
5. **Paying for a card.** Paymob (online, automatic — the callback activates the card), or through customer services: **cash on delivery**, **Vodafone Cash**, **Instapay** (the last two with a receipt upload). Two plans, both admin settings: yearly (`membership_price`, `membership_months`) and half-year (`membership_half_price`, `membership_half_months`); a price of 0 = that plan is not sold. Clients draw `status.plans` (`year`/`half`, each with price and months) and send the chosen one as `plan`; the backend refuses a plan that is not on sale and charges ITS price (`MembershipPlan::find`). Every accepted payment writes a `member_payments` row (`ActivateSubscription`), with the plan's months. A receipt is a CLAIM: it never extends a card by itself — an admin confirms it at `/admin/subscription`. Only `ActivateSubscription` adds card time (a verified Paymob callback, or an admin pressing confirm); it is idempotent, so a repeated callback or click can never grant two periods. A trial becomes `full` and is paid from the day of payment. **Which methods are SHOWN is an admin switch** (`/admin/setting`, `App\Support\PaymentMethods`): `payment_paymob_card_enabled` and `payment_paymob_wallet_enabled` (Paymob by bank card / by mobile wallet such as Vodafone Cash — two separate buttons, each its own Paymob integration: `PAYMOB_CARD_INTEGRATION_ID`, `PAYMOB_WALLET_INTEGRATION_ID`; clients send `paymob_channel` = `card`|`wallet`; both default on), `payment_cod_enabled` (cash on delivery, default off), `payment_wallet_enabled` (wallet transfer / Vodafone Cash with receipt, default off), `payment_instapay_enabled` (default off). Orders and subscriptions are both gated by it and the backend refuses a hidden method; clients draw only `payment_methods` (`/mobile/shop`, `/partner/shop-settings`) and `status.payment_methods` — never a hard-coded list.
6. **Paymob callbacks** are public and trusted ONLY through the HMAC; a paid amount that is not the price is never accepted; every HTTP exchange is stored verbatim with timing in `order_payment_logs` (shared with orders). Subscription references are `SUB<id>A<attempt>`, order codes are `DL-XXXXXXXX` — never mix them.
7. **Relatives.** A card holds at most **15 first-degree relatives** (wife, husband, son, daughter, father, mother — siblings are second degree: customer service adds those). During the trial the owner CANNOT add any: the app/site shows "contact customer service" and a **"Call me to add my relatives"** button that files a `relative_request` in the contact inbox (one open request at a time). After the card is paid (and not expired) the owner can add relatives themselves — each is created **pending** (`added_by = member`), never active, until an admin approves.
8. **Admin must hear about pending work.** A member-added relative also files a `pending_relative` inbox message; the admin sees banners + sidebar badges (`AdminAlerts`), a **"Pending relatives"** filter and a **"Trial"** filter on the members list, and a pending-count badge per row. Manual payments wait in `/admin/subscription`. Do not add a way to create an active relative from a member-facing endpoint.
9. **Profile nudge.** While a signed-in member's profile is incomplete, the website and the app show a small notice **every 60 seconds** with the percentage (`progress.overall.percent`) and what is missing (address, job title, email, …). It also says: to add relatives contact customer service, and a card holds up to 15 first-degree relatives. It stops by itself at 100%. The figure is `RegistrationProgress` in the backend — clients never count fields.
10. **Errors are logged on both sides** (see the error-logging rule in the backend `AGENTS.md`): backend `Log::error` with context; front ends report to `/api/v1/client-errors` (the website relays through its own `POST /client-errors`).
11. **Tests that pin this:** backend `tests/Feature/TrialCardTest.php` and `PaymobPaymentTest.php`; website `tests/Feature/MemberTrialCardTest.php`. Run backend tests on a throwaway database (never the live one).
12. **Guest → trial flow (app and website alike).** A visitor leaves name + phone in the card popup → the client asks the backend `phone-check` (`has_card` only, NO SMS; the website uses the key-gated `partner/auth/phone-check`, the app `mobile/auth/phone-check`) → a phone with no card is offered the free card → confirm name + phone → OTP → **gender** → `POST /membership/trial` (`gender` male|female; optional on the backend, required by both UIs). Registering at the code leaves an inert `REG-` row; the card goes active only when the trial form is submitted. The trial (amber) and expired (red, "no discount, full price") reminders repeat every 60 s and lead to payment. Admin: the members list shows a Trial badge with a ✕ to remove it by hand, a *Paid from the app* filter and per-method filters (Paymob / Vodafone Cash / Instapay / cash), and the show page lists every subscription payment with its receipts; confirming a payment removes the trial automatically (`ActivateSubscription`). Payments record `channel` (`mobile`/`website`).

### Where it lives (backend)
- `App\Actions\Membership\{StartTrialCard, StartSubscription, ActivateSubscription, ApplyPaymobSubscriptionTransaction}`, `App\Support\{MembershipPlan, MembershipStatus, AdminAlerts}`, models `TrialClaim`, `MembershipSubscription`.
- Member API (token): `GET /api/v1/membership`, `POST /membership/trial|subscribe|relatives-request`. ## Contact Enquiries Feature Notes
- `contact_messages` is the ONE inbox for every public form, this site's and the Deilar storefront's. `source` (`ContactSourceEnum`) is what tells them apart: `contact_form`, `card_popup`, `join_request`. Sales read the three differently, so it is a first-class filter, not something to search for.
- Storefront enquiries arrive at the key-gated `POST /api/v1/partner/contact-messages`. `$request->ip()` there is the STOREFRONT's server — the visitor's own `ip_address`, `user_agent`, `locale` and `referrer` come in the request body, exactly as they do for partner orders. That is why the endpoint needs the partner key.
- Write through `App\Actions\Contact\RecordContactMessageAction` — never `ContactMessage::create()` directly. It writes the row and its opening `received` log entry in one transaction, so an enquiry can never exist without a starting point in its log, and it tells the inbox. A mail failure is caught and logged there rather than thrown: the row is already committed, and a 500 makes the storefront queue a duplicate.
- Admin edits go through `App\Actions\Contact\UpdateContactMessageAction`, which writes one `contact_message_logs` row per field that actually moved. A salesperson is logged by NAME (so the trail survives that salesperson being deleted); a status by its VALUE (so it can be re-translated for whoever reads the log later). Never log a label.
- Statuses are a sales PIPELINE — `new` / `in_progress` / `resolved` / `closed` — not an inbox's read/unread. `read_at` records the first time an admin opened it and moves nothing; `replied_at` is stamped the first time it reaches `resolved`.
- `commercial_register` belongs to `join_request` only: it is what sales verifies an applying facility against, so it appears in the list, the detail page and the inbox mail.
- `created_at` is accepted on the partner endpoint for the storefront's one-off backfill only, so a copied enquiry keeps its real age. The timestamps are deliberately NOT fillable; the action sets them on the instance.
- Permissions: reads (`index`/`show`) need `manage contact messages|manage memberships|view contact messages`; writes (`update`/`destroy`/`bulk-update`) need `manage contact messages|manage memberships`. `manage memberships` is kept on both so admins who could work the inbox before it had its own permission do not lose it. Both controller actions pass `canManage` to the page, and `Show.vue` hides the whole manage card behind it — the viewer role holds `view contact messages`, so it reaches the page with no right to change anything.
- There is no "manage own contact messages". It used to sit in `pairs()`, was offered on `/admin/roles/create` and enforced nowhere; an enquiry comes from a public form and has `created_by = null`, so nobody can ever own one. `MANAGE_CONTACT_MESSAGES` is now in `standalone()`. Do not re-pair it.

## Geography: governorates → cities → areas

- Three levels, each with a `boundary` GeoJSON column that is NOT fillable and is hidden from every list payload — lists carry `boundary is not null as has_border`, the maps fetch geometry on their own (`admin.governorate.city-borders`, `admin.city.area-borders`). Write a border through `AdminBoundaryController` (query builder, `GeoJsonArea` rule) — a model save would re-run the slug generator.
- Cities live at `/admin/city` (list) and `/admin/city/{id}` (rename, delete, its areas, the map). Areas are added / renamed / deleted there, in JSON, never on their own page (`/admin/area` is the read-only list). Permissions are their own, apart from the governorates': `manage cities` / `view cities` and `manage areas` / `view areas` — standalone, no "own" variant, because neither table has a `created_by`. Cities: list, page, add/rename/delete, city border. Areas: the `/admin/area` list, add/rename/delete, area border, and the areas section of the city page (someone with `view cities` only sees the city; its areas and area map are hidden and the area routes 403). A governorate's own border stays on the governorate pair. The two map feeds (`admin.governorate.city-borders`, `admin.city.area-borders`) accept either family, since both the governorate map and the city page read them. On the governorate edit page the city rows are `locked` (zoom only) without `manage cities`. Migration `2026_09_20_160000` carried existing holders over (`manage governorates` → all four, `manage own`/`view governorates` → the two view ones); run `db:seed --class=PermissionSeeder` so the `viewer` role picks up the new view permissions.
- `BorderMap.vue` (`Pages/Admin/Governorate/_components/Form`) is the one border editor — the governorate edit page and the city page both feed it `targets`. Do not fork it.
- A city with facilities, branches, members' addresses or services pointing at it is NOT deletable (those FKs are `nullOnDelete`, so a delete would silently blank real places); its areas cascade.
- Areas added by hand get a generated `M…` pcode; imported ones are `EG…`. `AreaSeeder` upserts on `pcode`, so re-running it overwrites the name/border of an imported area that an admin edited — do not re-run it casually.
- Each governorate whose city borders leave ground uncovered has an "Unmarked City" (`City::UNMARKED_NAME`, `UnmarkedCitySeeder`, `egypt-unmarked-boundaries.json`); Cairo has none.
- Areas are filed under the SMALLEST city border holding their centre, else their governorate's Unmarked City (`egypt-area-boundaries.json` carries the key; `AreaSeeder::refile()` applies it moving only `city_id`/`governorate_id`, never a name or border an admin edited — migration `2026_09_20_170000`). A city can own no areas because the census units are bigger than it (Miami sits inside the Nasseriya area); its page then names that area via `App\Support\GeoJson`.
- **Run tests against a throwaway database, not the live one:** `APP_CONFIG_CACHE=/tmp/nocache.php DB_CONNECTION=sqlite DB_DATABASE=:memory: bin/php artisan test <file>` — bypasses the cached config, builds a fresh schema from the migrations (data the migrations do not seed, and MySQL-only SQL like `JSON_UNQUOTE` on the branch list, will not work there; write tests that create their own rows and create the permission rows they need).
- **Plain `php artisan test` hits the LIVE database on this host.** `bootstrap/cache/config.php` is cached, so phpunit.xml's `DB_DATABASE=membership_test` and `APP_ENV=testing` are ignored (`APP_ENV=production` also keeps CSRF on, hence the `withoutMiddleware` in new tests). `RefreshDatabase` only rolls each test back in a transaction — `migrate:fresh` is refused in production, which is the only thing protecting the data. Never write a test that commits (DDL, `DB::statement`, truncation), and prefer clearing the config cache / creating a test DB in hPanel.
- A facility branch has an OPTIONAL `area_id` (an area of ITS city, `AreaBelongsToCity` on every branch request; `FacilityBranch::saving` drops it whenever the city changes, so the form, imports and the AI place sweep all stay consistent). The branch forms (`FacilityBranchForm.vue` and the modal `FacilityBranchCard.vue`) share `BranchAreaSelect.vue`, which fetches only the chosen city's areas from `admin.facility.branch.city-areas` — never ship all 5,000+. An update that omits `area_id` keeps the stored one; one that sends it empty clears it. An area a branch names cannot be deleted. The migration exporter/importer and the spreadsheet branch import do not carry the area yet.
- Imported area names arrive from the census with the spaces stripped and no English. `php artisan areas:fix-names` (Gemini; needs outbound HTTPS, so not from the Claude sandbox) re-spaces the Arabic and adds English, resumable and only for areas with no English yet; the Arabic answer is accepted only if it has the SAME letters (`AreaNameFixer::sameLetters`), so the model can never rewrite a name. `--dry --limit=N` previews. `AreaSeeder::run()` would overwrite these names back to the census originals — use `refile()` instead.

## Visitors (website + Android + iOS)

- `visitors` = one row per device/browser, keyed by the client's own `visitor_key` (website cookie `dl_vid`, app install id); `page_visits` = one row per page/screen. Both live HERE; the website and the apps only relay.
- Write ONLY through `App\Actions\Visitor\RecordVisitAction`. A later hit enriches the same visitor (GPS, governorate/city via `ResolveVisitorPlace`, phone, email, name) and never overwrites a known value with an empty one.
- Endpoints: `POST /api/v1/partner/visits` (key-gated; the visitor's own `ip_address` / `user_agent` come in the body) and `POST /api/v1/mobile/visits` (`platform` android|ios; the IP is the request's own, a body IP is ignored). Both go through `StoreVisitRequest`.
- `visitors.user_id` / `membership_id` are set ONLY from a verified Sanctum bearer token (`$request->user('sanctum')`). A phone/email typed into a form is stored as a claim and never links a member.
- Admin: `/admin/visitors` (+ show), and the **Visitors** tab on the product page (`GET /admin/product/{slug}/visitors`), permission `view visitors` (added by a migration; do NOT re-run PermissionSeeder to get it).
- Old website rows: `php artisan visits:import-website` (set `WEBSITE_DB_*`; `--dry` first). Re-runnable via `page_visits.legacy_id`.
- **Charts** (the website dashboard's, moved here): `App\Actions\Visitor\SummariseVisits` (per day, per page, per source, top products/facilities, busiest day; 7/30/90 days; unique = distinct `visitor_id`; cached 5 min). Drawn at the top of `/admin/visitors` (`GET /admin/visitors/stats`, `VisitsCharts.vue` — one line per source so website vs Android vs iOS read side by side) and served to the website dashboard by the key-gated `GET /api/v1/partner/visits/summary` (the website asks `source=web`; it reads it when `ANALYTICS_STATS_FROM=membership`).
- **Source filter**: `web`, `android`, `ios`, or `mobile` = both apps (`VisitSourceEnum::forFilter`) — on the charts, the visitors list and the product tab. Never compare `source` to a filter value directly.
- **Retiring the website's own table**: import (`visits:import-website --dry`, then for real) → set the website's `ANALYTICS_STATS_FROM=membership` and compare its dashboard → `ANALYTICS_LOCAL=false` → back up and only then drop its `page_visits` in a later release.
- **Timezones: this app is `Africa/Cairo`, the website is `UTC`.** Every `visited_at` is stored in OUR timezone: `RecordVisitAction` converts the caller's ISO time (`->setTimezone(config('app.timezone'))` — a Carbon is saved as its own wall time, so an unconverted `+00:00` lands three hours early), and `visits:import-website --timezone=UTC` converts the website's rows. Migration `2026_10_23_130000` repaired the rows written before that (ids 1..69682, fingerprinted to the live DB). Charts bucket days in Cairo time, so per-day figures differ slightly from the website's old UTC days; window totals match.
- **Import cutoff**: the website started relaying at `2026-10-22 14:44:12` UTC. Website rows from then on reach us by relay, so a top-up import must use `--until="2026-10-22 14:44:12"` or it copies them twice.
- Tests: `tests/Feature/VisitorTrackingTest.php` (needs a throwaway MySQL database — the sqlite schema build is broken by an old migration).
